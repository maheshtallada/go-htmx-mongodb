A1 — Micro-questions (assignment-specific answers)

1. Why does Go return errors instead of throwing exceptions?

Go treats errors as values so handling is explicit and local. Returning errors makes control flow obvious: callers receive the error value and decide how to respond. This avoids hidden control flow from exceptions and helps with clear resource cleanup (no automatic stack unwinding). The language and idioms encourage immediate, simple error checks, which reduces surprising runtime failures.

2. What is a sentinel error?

A sentinel error is a predefined package-level error value (for example, `ErrInsufficientFunds`) used to indicate a specific, well-known failure condition. It’s created with `errors.New(...)` and returned directly from functions for callers to detect.

- Callers should check it using `errors.Is(err, ErrInsufficientFunds)`, which still works if the sentinel is wrapped with `%w` to add context.
- Sentinels are good for simple, common errors. For richer error data, define a custom error type and use `errors.As` to extract fields.

Notes on wrapping and context:

- Returning the sentinel directly:
    return 0, ErrInsufficientFunds

- Wrapping with context (keeps sentinel discoverable):
    return 0, fmt.Errorf("pay %s: %w", item, ErrInsufficientFunds)

Both patterns are valid; prefer wrapping when you want extra context while keeping the sentinel detectable via `errors.Is`.

---

What is `w` for?

- `w` is the conventional name for the first parameter of HTTP handler functions: `func(w http.ResponseWriter, r *http.Request)`.
- Its type, `http.ResponseWriter`, is an interface used to build the HTTP response: set headers, status codes, and write the response body.

Common uses:

    w.Header().Set("Content-Type", "text/html")
    w.WriteHeader(http.StatusOK) // must be called before writing body to set status code
    fmt.Fprintln(w, "Hello, world") // writes body to client

Notes:
- Do not store `w` for use outside the request handler; it is only valid for the lifetime of the request.
- The name `w` is just a convention (short for "writer"); any valid identifier may be used.
- `fmt.Fprintln(w, "text")` writes to the HTTP response body. It does not automatically print to the terminal. If you want output in the terminal too, do a separate `fmt.Println("text")`.

What does %w mean in fmt.Errorf?

- %w is the formatting verb used by fmt.Errorf to wrap an existing error value into a new error that carries additional context while preserving the original error as the cause.
- The wrapped error can be inspected with errors.Unwrap and identified with errors.Is or extracted with errors.As.

Example:
    return 0, fmt.Errorf("pay %s: %w", item, ErrInsufficientFunds)

This produces an error whose Error() string is, e.g., "pay coffee: insufficient funds" while errors.Is(err, ErrInsufficientFunds) returns true.

Notes:
- Use %v or %s to include the error text without wrapping; %w keeps the error chain for unwrapping.
- Only wrap actual error values with %w (not strings).
- The purpose of wrapping is to preserve the original sentinel or underlying error while adding context. For example, `fmt.Errorf("pay %s: %w", item, ErrInsufficientFunds)` keeps the sentinel detectable with `errors.Is`, but still gives the user a more specific message.

A3 — Micro-questions (error matching and wrapping)

1. Difference between `errors.Is` and `errors.As`?

`errors.Is` checks whether an error in the chain equals a target value (a sentinel). Use it to detect known sentinel errors like `ErrInsufficientFunds` even if they are wrapped. `errors.As` looks for a concrete error type in the chain (e.g. `*ValidationError`) and, if found, assigns it so you can read its fields.

Example:
    if errors.Is(err, ErrInsufficientFunds) { /* handle sentinel */ }

    var ve *ValidationError
    if errors.As(err, &ve) { fmt.Println(ve.Field) }

2. What does `%w` do that `%v` does not?

`%w` wraps the original error into the new error value, preserving the error chain so `errors.Unwrap`, `errors.Is`, and `errors.As` work. `%v` (or `%s`) only formats the error text into the new message and discards the original error's identity/type.

Example:
    // preserves chain
    return fmt.Errorf("pay %s: %w", item, err)
    // loses chain (only message kept)
    return fmt.Errorf("pay %s: %v", item, err)

3. When should you wrap vs. return the error unchanged?

- Wrap when adding useful context (operation, resource, field) that helps debugging or user messages, but you still want callers to detect the original cause. Example: wrapping a DB error with the failing query.
- Return the error unchanged (or return a sentinel directly) when you are the originator of a well-known error and want callers to match it exactly without extra context, or when no extra context is meaningful.
- Prefer wrapping the actual `err` returned by lower-level calls (not re-wrapping a different sentinel) so callers can still use `errors.Is`/`errors.As` reliably.

B2 — HTMX micro-questions

1. Why return `422` instead of `200` for a validation error?

A validation error is not a successful request; the request was accepted by the server, but the submitted data failed business rules. `422 Unprocessable Entity` is the conventional HTTP status for that case. It tells the client the input needs correction, while still letting HTMX process the returned HTML fragment.

2. Difference between `HX-Redirect` and `HX-Location`?

`HX-Redirect` tells HTMX to navigate the browser to a new URL as a full page load. `HX-Location` is used for client-side navigation updates where HTMX handles location changes without a simple full page replacement, typically for more controlled client-side transitions.

3. Why do server-side validation even if you also validate in the browser?

Browser validation is only UX and can be bypassed. Server-side validation is the real security and correctness boundary. It ensures the backend enforces rules even if a client is malicious, outdated, or manually edited.

C4 — MongoDB understanding

1. What does `1` vs `0` mean in a projection? Can you mix them?

In MongoDB projection, `1` means include the field and `0` means exclude it. For example, `{ customer: 1, total: 1 }` includes only those fields. The same projection cannot mix `1` and `0` for the same document unless you are excluding `_id` with `0` while including other fields. In practice, you usually either include fields with `1` or exclude fields with `0`.

2. What does `.sort({ total: -1 })` mean? What is `1`?

`sort({ total: -1 })` sorts by the `total` field in descending order (`-1` means descending, `1` means ascending). So a larger total appears first.

3. Why use `.limit()` for pagination performance?

`.limit()` restricts how many documents the server returns, reducing network load and memory usage. It helps pagination by fetching only a small page at a time instead of the whole collection, improving performance and responsiveness.
