Slices — quick reference (layman-friendly, concise)

1. What is a slice?
- A slice in Go is a lightweight view into an underlying array. Think of it as a flexible, resizable window onto a contiguous sequence of values.
- It consists of three things: pointer to the array, length (how many elements), and capacity (how many elements the underlying array can hold
from the start position).

2. Why use slices instead of arrays?
- Arrays have fixed size in their type (e.g., [3]int) and are rarely used directly.
- Slices are dynamic, easier to pass around, and are the idiomatic way to work with lists of values in Go.

3. Zero value and nil slices
- var s []int // zero value is nil
- A nil slice has length 0 and capacity 0. You can still append to it.

4. Common ways to create slices
- Literal with elements:
    s := []int{1, 2, 3}
- From an array:
    a := [5]int{0,1,2,3,4}
    s := a[1:4] // view elements 1..3
- Using make (specify length and optional capacity):
    s := make([]int, 3)       // len=3, cap=3, zero-valued elements
    s2 := make([]int, 0, 10)  // len=0, cap=10 (reserve space)

5. Append and growth
- s = append(s, 4) // returns a new slice value (often same backing array or a new one if capacity exceeded)
- append may allocate a new underlying array when capacity is insufficient.

6. Length and capacity
- len(s) returns the number of elements
- cap(s) returns the capacity (how many elements can be stored before reallocation)

7. Indexing and slicing
- Access: v := s[0]
- Set: s[1] = 10
- Slice sub-slice: t := s[1:3] // includes index 1,2 (exclude 3)

8. Copy
- copy(dst, src) copies elements; dst must be a slice with enough space

9. Nil vs empty slice
- var s []int // nil, len=0, cap=0
- s := []int{} // empty slice, len=0, cap=0 but not nil
- Both behave similarly for iteration and append; some APIs check for nil vs non-nil.

10. In context of engineers list
- In day2/htmx/server.go we used:
    var engineers = []Engineer{...}
  This is a slice of Engineer values. It holds multiple Engineer elements and can grow with append.
- The slice is not an array; it's a dynamic collection backed by an array managed by Go.

11. Cheatsheet examples
- Declare empty: var s []string
- Literal: s := []string{"a","b"}
- Make with capacity: s := make([]string, 0, 5)
- Append: s = append(s, "c")
- Iterate: for i, v := range s { ... }

12. Common pitfalls
- Taking address of loop variable: for i := range s { p := &s[i] } // safe; but &v when using range value is wrong
- Assuming append mutates in-place (it returns new slice value; always assign result)


End of slice notes.


CRUX: slice literal vs array literal

- The code `var engineers = []Engineer{ {1, "Mahesh", "Senior Lead"}, {2, "Asha", "SDE II"}, }` is a slice literal, not an array.
 The square-brackets without a length (`[]Type{...}`) create a slice whose backing array is allocated and filled with the listed elements.
- An array literal uses a fixed length in the type, e.g. `[2]Engineer{ ... }`. Arrays embed their length into the type ( `[2]Engineer`
and `[3]Engineer` are different types ).
- Slices are the idiomatic, resizable collection in Go. A slice literal is simply a convenient way to create a slice with initial elements;
it does not make the variable an array.

Why the Engineer type appears twice in the repo (server.go vs day2/go)

- Small examples often duplicate a simple struct definition inside different packages for isolation and simplicity (e.g.,
a server example re-declares the small type it needs).
- To *reuse* a single type across packages, you must put it into a shared package (not `main`) and import that package where needed.

Recommended options (crux and tradeoffs)

1) Leave the simple duplicate (fast, minimal change)
   - Pros: simplest, no refactor needed.
   - Cons: duplication; if the struct changes you must update both places.

2) Create a shared package (recommended for real projects)
   - Move the struct and its methods into a package like `day2/models` or `day2/engineer` (package name is lower-case).
   - Import that package from the server and tests: `import "day2/engineer"` or similar.
   - Pros: single source of truth; tests and server use same type and methods.
   - Cons: slightly more refactor work up-front.

3) Use separate DTOs in each package and map between them
   - Useful if server needs only a subset of fields or different json/tpl tags.
   - Adds mapping code but decouples concerns.

TEMPLATES: what is the value passed to `{{range .}}`?

The actual value is the Go variable `engineers`:

```go
var engineers = []Engineer{
    {1, "Mahesh", "Senior Lead"},
    {2, "Asha", "SDE II"},
}
```

This is a slice of `Engineer` values.

Then the server does this:

```go
tmpl.ExecuteTemplate(w, "page", engineers)
```

Meaning: pass the whole slice as the template data.

Inside the template:

```gotemplate
{{range .}}
  <li id="eng-{{.ID}}">
    {{.Name}} - {{.Role}}
  </li>
{{end}}
```

This is the flow:

- `.` at the top level is the whole slice (`engineers`)
- `{{range .}}` says: iterate over each element of that slice
- each iteration gives one item
- that item is a single `Engineer` struct
- inside the loop, the dot (`.`) is now that one `Engineer`
- so `.ID`, `.Name`, `.Role` mean: read the ID, Name, Role fields from this single Engineer

Example:

- first iteration: current item = `{1, "Mahesh", "Senior Lead"}`
  - `.ID` => 1
  - `.Name` => "Mahesh"
  - `.Role` => "Senior Lead"

- second iteration: current item = `{2, "Asha", "SDE II"}`
  - `.ID` => 2
  - `.Name` => "Asha"
  - `.Role` => "SDE II"

So the item is not the `h1` heading and not a separate "Engineers" object.
`h1` is just plain static HTML. The loop is only iterating the slice.

It is effectively a template loop, not an HTML loop. It's Go template syntax that generates repeated HTML for each item in the slice.

This is the important point to remember:

- outer data passed to template = slice of Engineer
- inside `range` = one Engineer at a time
- `.Name` / `.Role` are fields of that one Engineer
